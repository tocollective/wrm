# LA/IX

Первый этап микроядра на M для WRM.081632: собственный старт, стек ядра,
сохранение контекста исключений и аварийная диагностика через UART.
После самопроверки входа ядро запускает экранную демонстрацию.
Есть bitmap-распределитель физических страниц с владением и отображение MMU
с защитой стека. Планировщика, IPC и пользовательских процессов ещё нет.

Из корня репозитория:

```sh
./laix/build.sh
./laix/run.sh
```

Нужны Python 3, готовый эмулятор `bin/wrm081632` и готовый ROM
`bin/firmware.rom`. Для других путей используйте переменные
`WRM_EMULATOR=/путь/к/wrm081632` и `WRM_ROM=/путь/к/firmware.rom`.
Скрипты работают из любого каталога. Аргументы `run.sh` передаются эмулятору:

```sh
./laix/run.sh --no-net
```

`build.sh` создаёт загрузочный образ `build/laix.img` и карту
символов `build/laix.map`. Собственный `src/start.asm` задаёт заголовок
`WRMB`, линкер выравнивает образ до секторов по 512 байт; файловая система и отдельный
загрузочный сектор не нужны. Это образ для WRM.081632, не для x86 BIOS.
`run.sh` подключает его как флоппи (`--floppy`); прошивка загружает ядро
по адресу `0x00010000`. Растры шрифта находятся после загрузочной части
образа и читаются ядром по необходимости. Флоппи сохраняет исходную
скорость 62 500 байт/с. Для запуска с диска 0: `LAIX_BOOT=hdd ./laix/run.sh`.

- `src/main.m` — точка входа, начинайте писать ядро здесь.
- `src/defs.m` и `src/defs.inc` — именованные значения аппаратных регистров,
  флагов, адресов устройств, протокола загрузки и размеров страниц.
  Тесты сверяют значения M и ассемблера без сборки.
- `src/start.asm` — boot-заголовок, проверка RAM, обнуление BSS,
  стек 8 КиБ, ранний обработчик без стека и вызов `main(0, null)`.
- `src/boot.m` — проверка и сохранение boot info, запуск самопроверок.
- `src/memory.m` — резервирование низкой памяти, образа и всей BSS,
  включая стек, guard page и две битовые карты. Метаданные страниц
  резервируются за BSS по фактическому размеру RAM (4 КиБ при 1 МиБ RAM).
  `allocPage()`/`freePage()` учитывают владельца и назначение; пользовательские
  страницы обнуляются. `allocTaskPages()` откатывает частичную выдачу,
  `freeTaskPages()` возвращает набор при дальнейшей ошибке подготовки задачи.
  `physicalPageAvailable()` проверяет свободу, `physicalPageOwned()` — владение.
  Ссылки MMU запрещают освобождение отображённых кадров и живых таблиц.
- `src/mmu.m` — начальное тождественное отображение RAM, VRAM и MMIO
  для supervisor mode; страница под стеком остаётся недоступной.
  Каталог и таблицы выдаются распределителем. `mmuCreateAddressSpace(owner)`
  создаёт каталог с общими supervisor-отображениями; `mmuInitAddressSpace()`
  поддерживает заранее выделенный каталог. `mapPage()`/`unmapPage()`/
  `setPagePermissions()` работают с принадлежащими задаче страницами в окне
  `0x40000000…0xBFFFFFFF`. Есть разделение superpage, FENCE/TLBI.ALL,
  переключение PTBR/ASID и уничтожение с учётом ссылок.
  W^X учитывает все алиасы кадра: физическое окно ядра становится R,
  пока кадр исполняемый; общие таблицы RAM распространяют права на все каталоги.
  Пользовательский стек не получает X, MMIO/VRAM остаются без U/X.
  Контракты — в [этапе 2](docs/02_MEMORY_MMU.md).
- `src/trap_frame.m` и `src/trap_layout.inc` — общий формат контекста
  на 160 байт и соответствующие ассемблерные смещения.
- `src/trap.m` и `src/trap.asm` — сохранение регистров, обработка
  `BREAK`/`SYSCALL`, восстановление и `IRET`. Принимаются только
  `BREAK`/`SYSCALL` self-test, заранее взведённые `trapExpect`; любой
  другой вызывает panic. Вход из user mode загружает
  доверенный стек через `KERNEL_SP(r0)`, вход из supervisor сохраняет текущий.
- `src/trap_test.asm` — самопроверка GPR (включая `tp` и `ra`), `sp` и `FCSR`
  через `BREAK` и неизвестный `SYSCALL`; syscall проверяет также сохранение `r2`–`r31`.
- `src/panic.m` и `src/debug_uart.m` — дамп исключения без экрана,
  диска и распределителя памяти; аварийный выход с кодом 254.
  `debugPrint(format, ...)` поддерживает `$s`, `$i`, `$u`, `$h` и `$$`;
  `$h` выводит восемь заглавных hex-цифр без префикса.
  Для десятичных чисел доступны ширина и нулевое заполнение (`$02i`);
  ширина ограничена 32 символами. Неизвестные подстановки и подстановки
  без аргумента остаются в тексте. `panic(format, frame, ...)` передаёт
  аргументы в UART-форматирование, например
  `panic("invalid address=$h", frame, address)`.
- `src/console.m` — собственная экранная консоль: 640×480, белый текст
  на чёрном фоне, перенос строк и прокрутка, без прерываний. Проверяет,
  что видеокарта приняла режим, и `ERROR` после каждой команды engine.
  При первом отказе (режим, engine, шрифт, VRAM, кеш глифов) консоль
  перестаёт рисовать и один раз пишет причину в UART:
  `LA/IX: console failed: …`; ядро продолжает работу.
- `src/font/font.m` — загрузчик бинарного шрифта и двоичный поиск по Unicode;
  консоль 80×30, ячейка 8×16, широкий символ занимает две ячейки.
- `src/font/data.m` и `src/font/data.asm` — подключение шрифта через
  `.incbin`, только заголовок и индекс, без растров в ядре.
- `src/font/glyph_cache.m` — чтение страниц растров с загрузочного диска и
  кеш на 256 глифов в VRAM, с вытеснением по FIFO.
- `src/rnd.m` — драйвер RNG: чтение 32-битного слова, заполнение
  байтового буфера и проверка воспроизводимого режима.
- `fonts/unifont-console.laf` — все 57 084 глифа Unifont 15.1.05 из
  `vendor/SDL/test/unifont-15.1.05.hex`, независимо от текста программы.
  Лицензия: `fonts/LICENSE-Unifont.txt`.
- Исходники LA/IX не импортируют и не собирают исходники прошивки.
  Консоль напрямую управляет видеокартой; сообщения ядра и аварийные дампы
  идут отдельно в UART (stdout эмулятора).
  Для отображения текста запускайте эмулятор с окном, без `--headless`.
- Сборочный сценарий компилирует модули по отдельности и компонует их
  с собственным стартом через `ld.py --layout boot`. Стандартные `crt0`
  и `trap` M не используются; `memcpy`/`memset` остаются из runtime M.
  Возврат из `main` считается аварией.

При входе от прошивки стек растёт вниз от `0x00010000`; собственный старт
переключает его на выделенный стек в BSS. Стек и страница под ним
выровнены на 4 КиБ. `kernelInit()` включает MMU до самопроверок и консоли;
guard page не отображается. Прерывания пока отключены.
Слова `0x1FF0`–`0x1FFC` в конце страницы boot info зарезервированы для
`KERNEL_SP`, границ текущего стека и временного `r1`; boot info и таблица
устройств должны заканчиваться ниже `0x1FF0`. Страница 0 не отображается,
поэтому NULL в ядре после включения MMU даёт page fault.
Старт инициализирует их загрузочным стеком. Будущий планировщик обновляет
доверенный стек и его границы перед запуском задачи с выключенными IRQ.
`kernelInit()` отдельно проверяет возврат из встроенного `breakpoint()` и
контролирует `IE = 0`, PIC `ENABLE = 0` до и после самопроверок.

Проверки исходников без генерации кода и сборки:

```sh
python3 -B -m unittest discover -s laix/tests -p 'test_*.py'
```

`tests/run_ready.py` проверяет уже готовые образы `tests/trap.m`,
`tests/trap_fault.m` и `tests/stack_guard.m` с их картами символов. Он не
собирает код и запускает тесты без добавленных растров шрифта. Например:

```sh
python3 -B laix/tests/run_ready.py --case trap /путь/trap.img /путь/trap.map
```

Для аварийных образов используются `--case trap_fault` и `--case stack_guard`.
Runner сверяет код выхода, полный UART-дамп и точный `EPC` из карты;
пустой вывод с успешным `HLT` не считается прохождением теста.
Для этапа MMU подготовлены дополнительные CPU-сценарии; их образы ещё
не собирались и не запускались. Их проверки уже подтверждены на готовом
`laix.img` через `tests/probe_mmu_cpu.py`: 13 запусков, реальные вызовы
MMU API и faults, без сборки. [Отчёт и SHA-256](tests/MMU_ACCEPTANCE.md).
Повторный прогон:

```sh
python3 -B laix/tests/probe_mmu_cpu.py laix/build/laix.img laix/build/laix.map
```

Для отдельных образов `LAIX_MAIN` выбирает соответствующий
`tests/<case>.m`; сборочный сценарий подключает общий `mmu_probe.m/.asm`
для четырёх тестов MMU. Runner принимает следующие case:

| Case | Проверка | Ожидание |
| --- | --- | --- |
| `mmu_remap` | remap в другой кадр, пересоздание таблицы, RO→RW | `MMU remap runtime OK`, exit 0 |
| `mmu_unmap` | доступ сразу после unmap прогретого VA | CAUSE=9, BADADDR=0x40000000 |
| `mmu_protect` | запись после RW→R прогретого VA | CAUSE=10, BADADDR=0x40000000 |
| `asid_reuse` | ASID 7→0→7 для разных владельцев | новое содержимое VA; CAUSE=9 по старому VA 0x40001000 |
| `text_write` | запись в `.text` | CAUSE=10 |
| `rodata_write` | запись в `.rodata` | CAUSE=10 |
| `data_exec` | исполнение из `.data` | CAUSE=8 |

Fault-сценарии требуют полный panic dump, точный EPC из карты и exit 254.
Например, для уже готовых артефактов:

```sh
python3 -B laix/tests/run_ready.py \
  --case mmu_remap /путь/mmu_remap.img /путь/mmu_remap.map \
  --case asid_reuse /путь/asid_reuse.img /путь/asid_reuse.map
```

`tests/probe_boot.py` проверяет тот же готовый `trap.img` через локальный
monitor: грязную BSS, копию boot info, стек, выключенные IRQ и точные
регистры/адрес продолжения для каждого `BREAK` и `SYSCALL`.
`tests/probe_unexpected_traps.py` проверяет неожиданные BREAK/SYSCALL на
готовом образе с `trapExpect`, включая реальные исключения CPU из user mode:

```sh
python3 -B laix/tests/probe_unexpected_traps.py laix/build/laix.img laix/build/laix.map
```

Monitor меняет ожидание и сохранённый контекст во временной машине; для
user mode добавляет временный RXU alias и выполняет IRET с недоступным SP.
Все 10 сценариев требуют panic, исходный EPC, сохранённые GPR и выход 254;
сам образ и инструкции обработчика не изменяются. Логи и SHA-256 сохраняются
в `laix/build/acceptance/unexpected_traps/`. Нужен локальный сокет monitor.
`tests/probe_null_page.py` проверяет слова входа `0x1FF0–0x1FFC`, отсутствие
PTE страницы 0 и supervisor RW страницы 1, затем настоящий NULL call:

```sh
python3 -B laix/tests/probe_null_page.py laix/build/laix.img laix/build/laix.map
```

Probe временно отображает существующую инструкцию вызова из ROM и задаёт
нулевой адрес в сохранённом контексте; код ядра и PTE страницы 0 не меняет.
Использует UART-проверки case `null_call` из `run_ready.py` с адресом возврата
тестового вызова: CAUSE=8, EPC=BADADDR=0, exit 254. Логи и SHA-256 находятся
в `laix/build/acceptance/null_page/`. Отдельный `tests/null_call.m` по-прежнему
проверяется через `run_ready.py`, когда готов его образ и карта.

`tests/probe_stack_overflow.py` проверяет аварийный путь при исчерпанном
стеке на готовом `laix.img`, без сборки:

```sh
python3 -B laix/tests/probe_stack_overflow.py laix/build/laix.img laix/build/laix.map
```

Monitor задаёт SP на нижней границе и возвращает CPU в существующий пролог
`main`: выделение стека и store вызывают настоящий page fault в guard.
Probe сверяет раннюю строку со SP, полный dump, все GPR и управляющие
регистры в статическом TrapFrame, вызов `trapBadStack` на аварийном стеке
и выход 254. Guard и обычный стек не изменены входом в обработчик.
Логи и SHA-256 — в `laix/build/acceptance/stack_overflow_probe/`.
Это проверка аварийного пути; отдельный рекурсивный образ
`tests/stack_overflow.m` запускается через case `stack_overflow`, когда готов.

Критерии первого этапа для supervisor mode подтверждены на эмуляторе;
результаты и команды — в [tests/ACCEPTANCE.md](tests/ACCEPTANCE.md).
Пролог user entry выбирает доверенный стек по `KERNEL_SP`, не обращаясь
к памяти через пользовательский `sp`. Реальная user-задача пока не запускается.
Вложенные исключения не поддерживаются: `EXL` остаётся установленным
до `IRET`, а ошибка самого обработчика приводит к double fault CPU.
Блок сведений о машине находится по адресу `0x00001000`; старт сохраняет
его адрес из `r1`, а `kernelInit()` копирует проверенный блок в
`kernelBootInfo`. Формат описан в
[протоколе загрузки](../docs/SPECIFICATION.md#boot-protocol), соглашения
о вызовах — в [ABI](../docs/ABI.md), язык — в [спецификации M](../m/docs/spec/README.md).
План и состояние реализации описаны в [docs/KERNEL.md](docs/KERNEL.md).
Каждый из шести этапов имеет отдельный документ с чек-листами реализации
и проверки; первый этап — [docs/01_BOOT_TRAPS.md](docs/01_BOOT_TRAPS.md).

## Проверки входа ядра

Без сборки:

```sh
python3 -B -m unittest discover -s laix/tests -p test_kernel.py -v
python3 -B -m unittest discover -s laix/tests -p test_memory.py -v
python3 -B tools/m.py --check laix/src/main.m
python3 -B tools/m.py --check laix/tests/trap.m
python3 -B tools/m.py --check laix/tests/trap_fault.m
sh -n laix/build.sh
```

При обычной загрузке перед экранной консолью выполняются самопроверки
сохранения GPR/`sp`/`FCSR` через `BREAK` и результата неизвестного
`SYSCALL`. Успех сообщается в UART строкой
`LA/IX: TrapFrame and syscall self-tests passed`.

Для отдельного runtime-сценария сборочный сценарий принимает `LAIX_MAIN`
с путём к `tests/trap.m` или `tests/trap_fault.m`. Первый завершает
машину с кодом 0 после самопроверок. Второй вызывает невыровненную
загрузку и ожидает дамп `CAUSE=3`, `BADADDR=00001001`,
`stage=trap-fault-test` и выход 254; адрес `EPC` должен совпасть с
`trapFaultInstruction` в карте символов. Оба сценария используют собственный
runtime LA/IX; обычный `m/tests/run.py` для них не подходит.
Сценарии не инициализируют экран и пригодны для headless-запуска.
Статические проверки не заменяют исполнение этих сценариев на готовом образе.

`tests/test_memory.py` интерпретирует исходный алгоритм M без генерации
кода: проверяет резервирование, границы RAM, совпадение guard-региона
с последним регионом RAM и переход стека через границу 4 МиБ.
`tests/test_address_space.py` дополнительно проверяет операции отображения,
владение, откат, ссылки и порядок инвалидации/переключения PTBR/ASID.
Это проверка таблиц страниц, а не исполнения исключений CPU.
`tests/stack_guard.m`, выбираемый через `LAIX_MAIN`, намеренно пишет
в guard page при исправном `sp`; ожидаются `CAUSE=10`,
`BADADDR=&kernelStackGuard`, `EPC=&stackGuardFaultInstruction`,
`stage=stack-guard-test` и код выхода 254. Готовый образ из
`build/acceptance/stack_guard.img` повторно прошёл эту проверку без сборки;
результат относится к проверенному артефакту из отчёта приёмки.

Начальное отображение следует W^X: `.text` — RX, `.rodata` — R, данные,
стеки и остальная RAM — RW без X, VRAM/MMIO — RW, без разрешения user mode.
Страница 0, бывший стек firmware, guard page, ROM и адреса за установленной
RAM не отображаются. `start.asm` выравнивает `.rodata` и `.data` по
страницам, а ядро с BSS должно помещаться в первые 4 МиБ.
Для управляемых пользовательских кадров W^X действует во всех каталогах:
W- и X-алиасы несовместимы, физическое supervisor-окно исполняемого кадра
становится R до удаления последнего X. Для изменения кода ядро сначала
снимает X со всех алиасов. Проверки AST — `tests/test_wx_aliases.py`;
они не подтверждают исполнение новых операций на CPU.

## Бинарный Unifont

При сборке `tools/pack_unifont.py` преобразует весь исходный HEX в
`fonts/unifont-console.laf` и отдельно сохраняет заголовок и индекс в
`fonts/unifont-index.laf`. Ассемблер включает только индекс в `.rodata`.
После компоновки `tools/append_font.py` дописывает растры за пределами
числа секторов, указанного в заголовке WRMB: прошивка их не читает.
Для другого шрифта: `LAIX_FONT=/путь/font.hex ./laix/build.sh`;
переменная теперь принимает Unifont HEX, а не BDF.
Поддерживаются Unicode-коды до U+10FFFF, высота 16, ширина 8 или 16.
Покрытие определяется HEX-файлом: комплектный набор содержит глифы BMP,
но не все символы Unicode. Для emoji вне BMP нужен другой HEX.

При `consoleInit()` ядро проверяет заголовок, размеры, порядок и ширины
глифов. Индекс остаётся в образе ядра; кеш растров изначально пуст.
При первом обращении к глифу читается один сектор с 16 соседними глифами.
Контроллер диска переносит 512 байтов в выровненный буфер RAM, затем ядро
копирует страницу в VRAM. Кеш содержит 16 таких страниц (256 глифов),
при заполнении вытесняется самая старая загруженная страница (FIFO).
Попадание в кеш не читает диск и не копирует растры. Уже нарисованный
текст хранится в framebuffer и не зависит от дальнейшего вытеснения.
Поиск глифа — двоичный, без линейного перебора и ограничения в 512 глифов.
Новые строки, включая полученные во время работы, не требуют обновления
шрифта, если их символы есть в выбранном наборе.

Комплектный файл занимает 2 283 392 байта. При старте читаются только
456 704 байта заголовка и индекса плюс код ядра. Чтение самого индекса
с флоппи занимает около 7,3 секунды вместо 36,5 секунды для всего шрифта;
это расчёт по скорости носителя, не измерение времени запуска.
Кеш занимает 8192 байта VRAM плюс 512 байтов буфера RAM и небольшую
таблицу страниц. Вместе с экраном используется 315 392 байта VRAM.
Промах в кеше читает один сектор (около 8,2 мс на флоппи).
Размер полного файла на диске почти не меняется; уменьшена загрузочная
часть образа, а растры не хранятся целиком ни в RAM, ни в VRAM.

`prints(format, ...)` принимает вариативные аргументы напрямую:
`$i` — знаковое десятичное число, `$f` — `Float`, `$h` — hex с `0x`,
`$s` — строку UTF-8. `$$` выводит один `$`; неизвестные подстановки
остаются как есть и не расходуют аргумент.

```m
import { prints } from "console.m"

prints("answer = $i or $f, $h is also $s\n", 42, 42.0, 0x42, "correct")
// answer = 42 or 42.0, 0x42 is also correct
```

Тип аргумента должен соответствовать подстановке: целое для `$i`/`$h`,
`Float` для `$f`, указатель на строку для `$s`. Явные преобразования
для литералов из примера не нужны.
`$f` округляет до шести значащих цифр, сохраняет хотя бы одну цифру
после точки и использует экспоненту для модулей меньше `0.0001` или
не меньше `1000000`; поддерживаются `-0.0`, `inf`, `-inf` и `nan`.
Нулевой адрес в `$s` выводится как `(null)`.
При нехватке аргументов подстановка остаётся в тексте, без чтения за
пределами пакета; лишние аргументы игнорируются.
`print()` и `prints()` ждут кадр после всего сообщения.

`print()` принимает UTF-8, `putChar()` — Unicode-код (`UWord`).
Например, `print("д")`, `putChar('д' as UWord)` и `putChar(0x0434)`
выводят букву «д».
`"д" as UWord` преобразует адрес строки в число, а не извлекает код
символа. Символьные литералы с Unicode вне ASCII имеют тип `UWord`,
так что подходит и `putChar('д')`. ASCII и `\xNN` сохраняют тип `UByte`;
для ASCII можно писать `putChar('A' as UWord)`.
Некорректный UTF-8 и отсутствующие глифы выводятся как U+FFFD (`�`);
если в выбранном шрифте нет U+FFFD, используется `?`.
В строковых литералах M Unicode можно писать напрямую; экранирование
байтов сохраняется. Ошибочный индекс, недостаточная VRAM или отсутствие
секторов растров приводит к `consoleInit() == false`.
После ошибки чтения либо извлечения/замены загрузочного диска вывод
останавливается; `consoleFailed()` возвращает `true`. Восстановление
требует повторной инициализации с подходящим загрузочным носителем.
При инициализации пустого кеша подтверждается флаг `STATUS.CHANGED`
от вставки текущего носителя, в том числе через Drag & Drop. Последующие
изменения носителя проверяются при каждом обращении к кешу.
Составные emoji, комбинируемые знаки и
контекстное формирование глифов этим растровым выводом не реализованы.

Проверки без сборки:

```sh
python3 -B -m unittest discover -s laix/tests
python3 -B tools/m.py --check laix/src/main.m
python3 -B tools/m.py --check laix/tests/font.m
python3 -B tools/m.py --check laix/tests/cache.m
python3 -B tools/m.py --check laix/tests/rnd.m
```

`tests/font.m` также содержит runtime-тест загрузчика и поиска; `--check`
проверяет только его синтаксис и типы. Для отдельного запуска после сборки
можно использовать `python3 -B m/tests/run.py laix/tests/font.m`.
Для runtime-теста кеша сначала собирают `tests/cache.m` в boot-образ,
добавляют к нему растры через `tools/append_font.py`, затем запускают
полученный образ на флоппи или диске 0. Этот тест не запускается обычным
`run.py`: ему нужны дополнительные секторы шрифта.

## RNG

Драйвер обращается к устройству по адресу `0xFD00E000` через указатель
`volatile` только для чтения. Инициализация и прерывания не нужны.

```m
import { rngWord, rngSeeded, rngFill } from "rnd.m"

let value: UWord = rngWord()
let seeded: Bool = rngSeeded()
let mut bytes: UByte[16]
let ok: Bool = rngFill(bytes, 16)
```

`rngFill(buffer, size)` записывает ровно `size` байтов, начиная с младших
байтов каждого слова. Буфер может быть невыровненным; вызывающий код
обеспечивает его размер и доступность для записи. Каждые четыре байта
(включая неполную последнюю группу) требуют одного чтения `DATA`;
неиспользованные байты последнего слова отбрасываются. Пустой запрос
возвращает `true` без чтения RNG, даже с `null`; непустой запрос с `null`
возвращает `false`.

`rngSeeded()` читает бит 0 регистра `STATUS`, не расходуя случайные данные.
При `--seed=N` или `--deterministic` он возвращает `true`: поток
воспроизводим и не подходит для секретных ключей. В обычном режиме данные
поступают из криптографического генератора хоста. Драйвер не меняет режим
и не устанавливает seed.

`tests/rnd.m` содержит runtime-тест с `--seed=0`: эталонный поток ChaCha20,
размеры буфера 0–5 и 32 байта, границы записи и переход между блоками RNG.
Команда `--check` выше проверяет только синтаксис и типы этого теста.
