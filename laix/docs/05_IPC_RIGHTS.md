# Этап 5. IPC и права на объекты

[План ядра](KERNEL.md) · [Предыдущий этап](04_SCHEDULER_IRQ.md) · [Следующий этап](06_USER_SERVICES.md)

Статус: предстоит. Цель — две изолированные задачи обмениваются короткими
сообщениями через endpoint, а ядро проверяет полномочия каждого участника.
Зависимости: адресные пространства, безопасная работа с user-буферами,
блокировка и пробуждение задач.

## Начальный контракт

Для первого IPC достаточно синхронных send/recv с фиксированным верхним
пределом размера, например 32 байта. Если другой стороны пока нет,
вызывающая задача блокируется. Произвольные очереди больших сообщений,
разделяемая память и передача capabilities могут быть следующими улучшениями.

Предлагаемые вызовы: `send(endpoint, buffer, length)` и
`recv(endpoint, buffer, capacity)`. Номера, формат сообщения, максимальную
длину, коды ошибок и результат нужно зафиксировать в ABI LA/IX.
Большой результат нельзя молча вернуть в r3–r6: текущий syscall ABI
предусматривает результаты r1/r2 и сохранение остальных регистров.

## Что сделать

### Объекты и handles

- [ ] Ввести endpoint: идентификатор/поколение, состояние, очереди
  ожидающих отправителей и получателей, ссылки и владелец управления.
- [ ] Добавить отдельную таблицу handles каждой задачи: ссылка на объект,
  поколение и права send/receive/manage.
- [ ] Проверять наличие записи и её права в таблице вызывающей задачи.
  Числовой ID сам по себе не даёт права обращаться к глобальному объекту.
- [ ] Определить закрытие handle, уничтожение endpoint и правила копирования
  прав; выдача копии не должна расширять полномочия.
- [ ] Защитить от старых handles при повторном использовании слотов;
  определить поведение при исчерпании пространства поколений.
- [ ] Первоначальные права выдавать доверенным bootstrap-кодом.

Capabilities здесь можно начать как проверяемые ядром записи в таблице.
Они не должны зависеть от секретности или случайности числового handle.

### Передача и ожидание

- [ ] Проверить право, размер и полный диапазон user-буфера до изменения очередей.
- [ ] Скопировать короткое сообщение в принадлежащее ядру хранилище TCB
  до блокировки отправителя; не хранить только его сырой указатель.
- [ ] При отсутствии получателя атомарно поставить отправителя в очередь
  и Blocked; при отсутствии отправителя аналогично блокировать получателя.
- [ ] При встрече сторон передать ровно одно сообщение и разбудить нужные
  задачи ровно один раз; выбрать и описать порядок очередей, например FIFO.
- [ ] При записи результата получателю использовать его каталог либо
  проверенные физические страницы. Один и тот же user-адрес в текущем
  каталоге отправителя может обозначать совершенно другую память.
- [ ] Возвращать проверенный размер и статус; маленький буфер обработать
  по явному правилу без потери сообщения или частичного неописанного успеха.
- [ ] Идентичность отправителя задавать ядром/правами endpoint, если она
  нужна протоколу; не принимать пользовательское поле как доказательство личности.
- [ ] Запретить двойное включение задачи в очереди; защитить операции от IRQ.
- [ ] На уничтожение объекта, exit или fault стороны снять её ожидания,
  вернуть другой стороне ошибку и освободить ссылки.

### Запрос и ответ сервиса

- [ ] Определить минимальный протокол request/reply для следующего этапа:
  endpoint ответа или ограниченное reply-право на ожидающего клиента.
- [ ] Связать ответ с конкретным запросом; запретить повторный/чужой reply.
- [ ] Документировать, может ли задача отправить самой себе и когда
  такой вызов возвращает ошибку вместо вечной блокировки.
- [ ] Определить отмену ожидания при завершении сервиса; таймауты можно
  добавить после рабочего базового обмена.

## Что проверить

- [ ] Send раньше recv и recv раньше send завершаются одинаковым сообщением.
- [ ] Ожидающие задачи Blocked, не опрашивают endpoint в busy-loop.
- [ ] Несколько отправителей/получателей соблюдают выбранный FIFO-порядок;
  нет пропусков, дублей и двойных пробуждений.
- [ ] Отвергаются чужой, закрытый и устаревший handle, а также недостаточные права.
- [ ] Передача копии handle не повышает права; закрытие одной копии
  соответствует заданному времени жизни оставшихся ссылок.
- [ ] Неверный указатель, граница страницы, переполнение длины,
  слишком большое сообщение и малый буфер не повреждают ядро/чужую память.
- [ ] При разных данных по одинаковому VA копия попадает именно в память получателя.
- [ ] Смерть отправителя, получателя или уничтожение endpoint не оставляет
  вечных ожиданий, dangling pointers и утечек страниц/объектов.
- [ ] Два клиента получают каждый свой ответ; чужой и повторный reply отвергается.
- [ ] Длинный ping-pong проходит под вытеснением без потери сообщений.
- [ ] Завершение аварийной задачи во время IPC не мешает третьей задаче
  и не останавливает планировщик.

## Когда этап готов

Две реальные user-задачи в разных каталогах обмениваются сообщениями,
ожидание экономит CPU, права проверяются, а все пути ошибки завершаются
без зависших задач и повреждения памяти.
Общий контракт регистров — [syscall ABI](../../docs/ABI.md#system-calls).
