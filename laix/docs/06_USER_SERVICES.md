# Этап 6. Сервисы и драйверы вне ядра

[План ядра](KERNEL.md) · [Предыдущий этап](05_IPC_RIGHTS.md)

Статус: предстоит. Цель первой вехи — приложение получает вывод от
отдельного консольного сервера через IPC. Затем эту модель можно расширять
на экран, ввод, диски и файловые сервисы.

Сейчас `console.m`, шрифт, дисковые чтения глифов и RNG вызываются внутри
ядра. Их наличие не означает, что реализованы пользовательские серверы.
Зависимости: user-задачи, планировщик, IPC и права на ресурсы.

## Что сделать

### Запуск и права сервисов

- [ ] Создать bootstrap/init, который запускает сервер и клиент и выдаёт
  им разные права: серверу receive и нужное устройство, клиенту send.
  Первые образы и таблица ресурсов могут быть включены в boot-образ.
- [ ] Выделить серверу отдельные код, данные, user/kernel-стеки и каталог.
- [ ] Определить API создания задач/выдачи памяти и его полномочия;
  не открывать управление всеми задачами любому приложению.
- [ ] Передавать начальные endpoints и параметры в проверенном стартовом
  блоке либо по закреплённому bootstrap-протоколу.
- [ ] Определить регистрацию/обнаружение сервиса. Для первого клиента
  достаточно заранее выданного handle; универсальный registry необязателен.

### Первый консольный сервер

Безопасный простой старт — UART-вывод без DMA. Перенос экранной консоли
потребует также разобраться с видеокомандами и чтением шрифтов с диска.

- [ ] Задать сообщение вывода: версия/тип, длина, текст, результат и ошибки;
  использовать проверенный ограниченный размер IPC из этапа 5.
- [ ] Запустить receive-цикл сервера в user mode; в ожидании он Blocked.
- [ ] Выдать серверу минимальный доступ к UART или узкую операцию вывода;
  приложение не должно самостоятельно получать устройство.
- [ ] Реализовать клиентскую функцию вывода через IPC, затем request/reply.
- [ ] Обрабатывать недопустимые сообщения без выхода за буфер и без panic ядра.
- [ ] Сохранять порядок текста нескольких клиентов по документированному правилу.
- [ ] Перевести обычную экранную/текстовую демонстрацию из kernel main
  в приложение; ядро занимается задачами и переходами, а не печатным циклом.
- [ ] Сохранить аварийный debug UART в ядре независимым от сервиса,
  IPC, диска и пользовательской памяти.

### Экран, IRQ и DMA

- [ ] Переносить экранный драйвер, Unicode/шрифт и кеш как отдельные
  пользовательские компоненты после работоспособного консольного протокола.
- [ ] Выдать VRAM и MMIO только выбранному сервису, запретить X и доступ
  к посторонним устройствам; проверить права всех отображений.
- [ ] Передавать IRQ сервису уведомлением с блокировкой/пробуждением,
  а не вызывать user-функцию из аппаратного пролога ядра.
- [ ] Описать владение IRQ, маскирование, обслуживание level-события и
  подтверждение; необслуживаемая линия не должна создавать IRQ-storm.
- [ ] Отдельно определить доверие к DMA-драйверам. На WRM DMA использует
  физические адреса и игнорирует MMU: выдача полного DMA-MMIO позволяет
  устройству писать память вне user-пространства драйвера.
- [ ] Для недоверенного сервиса оставлять программирование опасных DMA
  команд за узким доверенным посредником с проверкой страниц/диапазонов,
  либо явно считать такой драйвер доверенным компонентом системы.
- [ ] Управлять жизнью DMA-буферов: физический адрес, выравнивание,
  владение, fence, завершение и запрет освобождения во время операции.
- [ ] Для шрифта заменить прямое дисковое чтение сервисным протоколом;
  не давать консоли неограниченные права на дисковый DMA ради одного глифа.
  Сейчас `cacheGlyph` передаёт диску виртуальный адрес буфера как физический;
  это верно только при identity map ядра.

MMU-изоляция обычного user-сервера сама по себе не обеспечивает изоляцию
драйвера с неограниченными DMA-регистрами. Поэтому первый тест отказа
нужно выполнять на сервере без таких полномочий.

### Отказ и дальнейшие сервисы

- [ ] При exit/fault сервера завершать его задачу, закрывать объекты по
  политике и возвращать ожидающим клиентам ошибку.
- [ ] Если предусмотрен перезапуск, выдавать новые права/поколения;
  старые handles не должны неожиданно обращаться к новому экземпляру.
- [ ] Перед уничтожением DMA-сервиса остановить устройство и дождаться
  прекращения обращений к памяти, затем освобождать буферы.
- [ ] Следующим отдельным сервисом добавить ввод; затем диск и файловый
  сервис. Для каждого закрепить сообщения, права и сценарий отказа.
- [ ] Отложить сеть, ELF-загрузчик и полноценную файловую систему до
  стабильного запуска/обмена/завершения простых сервисов.

## Что проверить

- [ ] На CPU одновременно работают ядро, user-сервер и отдельный клиент.
- [ ] Клиент пишет только через endpoint; прямой доступ к MMIO отвергается.
- [ ] Сервер спит без сообщений и корректно просыпается под вытеснением.
- [ ] Несколько клиентов получают правильные ответы и согласованный порядок вывода.
- [ ] Неверный тип, размер и текст сообщения не повреждают сервер/ядро.
- [ ] В сервере намеренно вызвать page fault: ядро и другой клиент продолжают работу.
- [ ] Заблокированные клиенты получают ошибку при смерти сервера, а не висят вечно.
- [ ] После перезапуска старый handle отвергается; новый сервер получает
  только предназначенные ему ресурсы.
- [ ] Kernel panic выдаёт дамп, даже если сервер вывода умер или заблокирован.
- [ ] Для добавленного IRQ нет потери пробуждений, повторных необслуженных
  IRQ и доступа другой задачи к линии.
- [ ] Для добавленного DMA отвергаются чужие страницы, неверные диапазоны
  и переполнения; буфер не освобождается до завершения операции.

## Когда этап готов

Первая веха завершена, когда клиент использует отдельный user-консольный
сервер через IPC, ожидание блокируется, права разделены и отказ этого
сервера не останавливает ядро. Перенос остальных драйверов — последующие
вехи с отдельной приёмкой по тем же правилам.
Аппаратные контракты — [UART, PIC, видео и DMA](../../docs/SPECIFICATION.md).
