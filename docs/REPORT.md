# WRM.081632: чего не хватает до полноценной машины

Отчёт по состоянию рабочей копии на 2026-10-01 (ветка `master`, включая
незакоммиченные `mmu.c`, `firmware/demos/*`). Цель — понять, что нужно,
чтобы на машине можно было запустить настоящую ОС (ядро с процессами,
файловой системой и вводом-выводом), а эмулятором было удобно пользоваться
и отлаживать программы.

## Что уже есть

- **CPU:** 32-битный RISC, 32 GPR, классический 5-стадийный конвейер с
  forwarding, load-use stall, предсказанием «не перейдёт», точными
  исключениями и прерываниями.
- **Режимы:** supervisor/user, `SYSCALL`, `IRET`, 7 control-регистров,
  13 причин исключений.
- **MMU:** двухуровневые таблицы, страницы 4KB и суперстраницы 4MB, права
  R/W/X/U, TLB на 64 записи с прямым отображением, `TLBI`.
- **Шина и память:** до 4 слотов RAM, ROM на 32MB, I/O-регион по странице
  на устройство.
- **Устройства:** PIC (32 линии, уровневые), клавиатура (HID usage ID, FIFO),
  UART (stdout/stdin хоста).
- **Тактирование:** 48 MHz, привязано к хостовому времени.
- **Инструменты:** ассемблер на Python (выражения, локальные метки,
  псевдоинструкции, `.include`/`.incbin`, листинг).
- **Прошивка:** демо, которое прогоняет все группы инструкций, прерывания,
  MMU и user mode.
- **Сборка:** нативная через SDL3 и веб через Emscripten.

Ядро процессора проработано хорошо. Основные пробелы — в периферии, в
нескольких архитектурных деталях, без которых ОС будет неудобно или
невозможно писать, и в инструментах.

## 1. Критично для запуска ОС

### 1.1 Таймер — нет ни одного источника времени

Сейчас нет ни программируемого таймера, ни счётчика тактов, доступного
программе. Без таймерного прерывания невозможна вытесняющая многозадачность,
а без счётчика — `sleep`, таймауты и измерение времени.

Предлагается:

- **Устройство `TIMER`** (например, `0xFD003000`, IRQ 2) с регистрами
  `COUNTER` (64 бит, две половины), `COMPARE` (или `RELOAD`) и `CONTROL`
  (enable, periodic/one-shot, ack). Линия остаётся поднятой, пока условие
  не сброшено, как у остальных устройств.
- **Регистры CPU** `CYCLE`/`CYCLEH` и `INSTRET`/`INSTRETH`, только для
  чтения. Значения уже считаются в `cpu->cycles` и `cpu->retired`, нужно
  лишь открыть их через `MFCR` (и, возможно, разрешить чтение из user mode).
- **RTC** (дата и время хоста) — желательно, но не срочно.

Попутно: устройства сейчас не тактируются. `machine_update` вызывает только
`cpu_update`, а у устройств нет `*_tick()`. Таймеру (и любому устройству с
задержками) нужен такой хук в цикле `machine_update`
([source/machine.c](../source/machine.c)).

### 1.2 Внешняя память — загрузить ОС неоткуда

В `config_t` уже есть `hdd_path[2]` и `floppy_path`, но они нигде не
используются. Весь код должен помещаться в ROM.

Предлагается **блочное устройство** (контроллер диска): регистры `SECTOR`,
`COUNT`, `BUFFER_ADDR` (физический адрес в RAM), `COMMAND` (read/write),
`STATUS` (busy/error/present), размер диска в секторах, IRQ по завершении.
Работать напрямую с RAM (DMA) проще и быстрее, чем через побайтовый порт
данных. Образ диска — обычный файл хоста (`hdd0.img`).

Ещё нужно описать **протокол загрузки**: ROM читает сектор 0 по
фиксированному адресу в RAM и прыгает туда (или грузит ELF). Это отдельный
раздел в `SPECIFICATION.md`.

### 1.3 Исключения в supervisor при `IE = 0` останавливают CPU

Сейчас любое исключение в supervisor mode с `IE = 0` делает halt
([cpu.c `cpu_stage_wb`](../source/cpu.c)). При этом обработчик входит именно
с `IE = 0`. Отсюда следствия:

- **Syscall и user-память.** Обработчик `SYSCALL`, который читает аргументы
  из user-памяти (аналог `copy_from_user`), остановит машину на первом же
  page fault. Demand paging и copy-on-write из syscall'ов невозможны, если
  ядро не включает `IE` вручную.
- **Смешанная семантика `IE`.** Флаг одновременно означает «разрешены
  прерывания» и «исключения можно обработать». Ядро не может запретить
  прерывания на время критической секции и при этом пережить в ней
  page fault.

Как исправить: разделить эти роли. Например, исключение в supervisor
обрабатывается всегда, а halt случается только при исключении внутри
обработчика до сохранения `EPC` (нужен флаг «в обработчике», аналог
`EXL` в MIPS). Другой вариант — отдельный вектор или стек для
double fault.

### 1.4 Нет атомарных операций

Нет ни `LL`/`SC`, ни `AMOSWAP`/`AMOADD`, ни `CAS`. На одном ядре supervisor
может защищаться отключением `IE` через `MTCR`, но user-код (futex,
lock-free очереди, runtime-библиотеки) не может сделать ничего атомарного.
Если когда-нибудь появится второе ядро или DMA, атомики станут обязательными.
Минимум — пара `LL rd, (rs1)` / `SC rd, rs2, (rs1)`, плюс `FENCE` на будущее.

### 1.5 MMU: мало информации для ОС

- **Нет битов Accessed/Dirty в PTE.** ОС не знает, какие страницы
  использовались и какие изменены, поэтому не может выбирать жертв для
  swap и писать обратно только грязные страницы. Можно либо выставлять A/D
  аппаратно (CPU пишет в PTE), либо явно документировать, что ОС должна
  эмулировать их через page fault (снимать `R`/`W`), и сказать об этом в
  спецификации.
- **Нет ASID и глобальных страниц.** Каждая запись в `PTBR` сбрасывает
  весь TLB, так что при каждом переключении процесса ядро и I/O-отображения
  промахиваются заново. Нужно поле ASID в `PTBR` и бит `G` в PTE. Для
  эмулятора это вопрос скорости, для архитектуры — полноты.
- **Нет запрета supervisor-доступа к user-страницам** (аналог SUM/SMAP в
  RISC-V). Не критично, но полезно для безопасности ядра.

### 1.6 Выключение и сброс машины

- **HLT.** После `HLT` эмулятор продолжает крутить пустое окно. Нет ни
  выхода из программы, ни кода возврата, ни вывода регистров.
- **Power/reset.** Нет устройства, через которое гость может выключить
  машину (с кодом выхода, что важно для тестов) или перезагрузить её.
- **Сброс с хоста.** `cpu_reset`, `pic_reset`, `uart_reset` и
  `keyboard_reset` существуют, но общего `machine_reset()` нет, как нет и
  горячей клавиши для него.

## 2. Процессор (ISA)

| Что | Зачем | Приоритет |
|---|---|---|
| `MULH`/`MULHU`/`MULHSU` | старшие 32 бита произведения: 64-битная арифметика, деление на константу в компиляторах | высокий |
| `BREAK` / `EBREAK` (новый `CAUSE`) | программные точки останова, `assert`, отладчик | высокий |
| Регистры `CYCLE`/`INSTRET` (см. 1.1) | профилирование, время | высокий |
| Регистр идентификации (`CPUID`/`VERSION`) | ОС должна проверять ревизию ISA и набор расширений | средний |
| `FENCE` / `FENCE.I` | порядок памяти, самомодифицирующийся код и JIT, когда появятся кэши или DMA | средний |
| Проверка reserved-битов | спецификация говорит «should be zero», но декодер их игнорирует; лучше явно решить: `illegal instruction` или «игнорируются» | средний |
| Отдельный стек или `SCRATCH` для user→kernel | уже есть `SCRATCH`; стоит описать рекомендуемую последовательность входа в ядро | низкий |
| Плавающая точка (F-расширение или soft-float ABI) | нужна компиляторам C и libc; на первое время достаточно зафиксировать soft-float | низкий |
| Векторизованные прерывания или приоритеты PIC | сейчас обработчик всегда один и читает `CLAIM`; приоритетов нет, выигрывает младшая линия. Для небольшой машины приемлемо | низкий |

### Замеченная проблема: спекулятивная выборка из I/O

IF выбирает инструкции по `pc+4`, `pc+8` до того, как EX разрешит переход, и
делает это обычным `bus.read`. Если соседняя виртуальная страница отображена
на I/O с правом `X` (или программа выполняет код рядом с концом региона),
выборка по ложному пути прочитает регистр устройства. Чтение `UART DATA` или
`KBD DATA` при этом **снимает байт из FIFO**, хотя инструкция будет отменена.

Решение: выборка из I/O-региона (`0xFD000000`–`0xFDFFFFFF`) — это всегда
fetch bus error без обращения к устройству. Лучше сделать это на уровне шины
отдельным флагом «fetch» или отдельным методом `bus.fetch`, и записать правило
в спецификацию. Аналогично стоит запретить обход таблиц страниц по
I/O-адресам (сейчас в спецификации только предупреждение о побочных
эффектах).

## 3. Периферия

| Устройство | Состояние | Что нужно |
|---|---|---|
| Таймер / RTC | нет | см. 1.1 |
| Диск | нет (есть неиспользуемые `hdd_path`, `floppy_path`) | см. 1.2 |
| **Видео** | окно 800×600 и текстура 640×480 создаются, но в текстуру ничего не пишется | framebuffer в RAM или VRAM (регистры: адрес, ширина, высота, формат, `VSYNC` IRQ) и/или текстовый режим 80×25 со шрифтом. `display_render` должен копировать framebuffer в текстуру |
| Мышь | нет | FIFO событий (dx, dy, кнопки), как у клавиатуры |
| Power / reset | нет | см. 1.6 |
| Звук | нет | необязательно; простой PCM FIFO через SDL audio |
| DMA | нет | можно встроить в дисковый контроллер |
| Перечисление устройств | нет | таблица устройств в ROM или ID-регистр в каждой I/O-странице (`+0xFFC`: тип и версия), чтобы ОС не хардкодила адреса |
| Отключаемые линии хоста | UART в браузере без ввода | ввод через поле на странице или xterm.js |

Шина: RAM ограничена одним слотом по 1MB (жёстко в `motherboard_create`).
Количество и размер слотов стоит брать из конфигурации.

## 4. Эмулятор (хост)

### 4.1 Конфигурация и запуск

- **Нет CLI.** `argc` и `argv` передаются в `application_create`, но не
  разбираются, а путь к ROM, частота и RAM зашиты в `config.c`. Нужны
  хотя бы `--rom`, `--ram`, `--clock`, `--hdd`, `--headless`, `--debug`,
  `--trace`.
- **Мёртвые поля конфигурации:** `debug`, `make_dump`, `window_scale`,
  `step_mode`, `hdd_path`, `floppy_path` объявлены, но не используются.
- **Нет headless-режима.** Без SDL-окна, до `HLT` или power-off, с кодом
  выхода. Он обязателен для автотестов и CI.

### 4.2 Отладка

Сейчас вся диагностика — одна строка `warning` при halt по исключению. Нужно
(примерно в порядке полезности):

1. **Дамп состояния при остановке:** GPR, `pc`, CR, содержимое конвейера,
   `cycles`/`retired`.
2. **Трассировка** (`--trace`): адрес, слово, дизассемблированная инструкция
   и записанный регистр на каждую retired-инструкцию.
3. **Дизассемблер.** Он пригодится и в C (для трассировки), и в Python (для
   `asm.py`). Таблица форматов уже есть в `cpu_decode`.
4. **Пошаговый режим и точки останова:** поле `step_mode` уже заведено, а
   также watchpoints на адреса.
5. **Символы.** Загрузка листинга или symbol-файла из `asm.py -l`, чтобы
   показывать `puts+0x14` вместо голого адреса.
6. **GDB remote stub** (TCP): позволит пользоваться `gdb` или `lldb`, когда
   появится компилятор. В перспективе.
7. **Дамп памяти** (`make_dump`).

### 4.3 Производительность и точность времени

- **Нет индикатора скорости.** Не видно, успевает ли эмуляция за 48 MHz.
  `clock_update` ограничивает догон ста миллисекундами, и если хост не
  успевает, машина тихо замедляется. Нужен индикатор (MIPS, % от
  реального времени) в заголовке окна или в выводе.
- **Нет быстрого пути для `WFI`.** Сейчас цикл всё равно прогоняет все
  такты по одному. Можно пропускать такты до ближайшего события таймера.
- **Функциональный режим (опционально).** Можно добавить режим без
  конвейера (одна инструкция за вызов) для скорости, оставив конвейерный
  режим для точного тайминга.

### 4.4 Прочее

- **Сохранение состояния.** Snapshot и restore (CPU, RAM, устройства)
  пригодятся при отладке ОС.
- **Обработка ошибок I/O.** `rom_load` не проверяет результат `ftell` и
  `fread`.
- **README.** Нет инструкции по нативной сборке. Команда `dd ...` создаёт
  пустой ROM, но не объясняет, как собрать прошивку. Стоит добавить
  `cmake -S . -B build && cmake --build build` и
  `python3 tools/asm.py firmware/main.asm -o bin/firmware.rom`.

## 5. Инструментарий

| Что | Состояние | Что нужно |
|---|---|---|
| Ассемблер | есть, хороший | макросы (`.macro`/`.endm`), условная сборка (`.if`/`.ifdef` — `-D` есть, но проверить значение в исходнике нечем), `.section`/`.bss` |
| Объектные файлы и линкер | нет, только монолитная сборка в плоский образ | формат объектников с релокациями (проще всего — ELF с собственным `e_machine`) и линкер со скриптом раскладки. Без этого нет раздельной компиляции и библиотек |
| Формат исполняемых файлов | нет | ELF или простой собственный заголовок; ОС нужно как-то грузить программы |
| Дизассемблер | нет | см. 4.2 |
| **Компилятор C** | нет | реалистичные пути: порт `chibicc`, `lcc` или `cproc`+`QBE` (бэкенд на ~1–2k строк), позже — бэкенд LLVM. Перед этим нужен ABI |
| ABI | описан только в комментарии `firmware/main.asm` | отдельный документ: роли регистров, стек и выравнивание, передача аргументов и struct'ов, соглашение syscall (номер в каком регистре, где результат, какие регистры сохраняются) |
| libc | нет | минимальная: `string.h`, `printf` поверх UART, `malloc` |

## 6. Тестирование

Автотестов нет вообще, есть только демо-прошивка, которую проверяют глазами.
Для процессора с конвейером это главный риск регрессий (forwarding, stall,
отмена инструкций, точность исключений).

Предлагается:

1. **Headless-режим с кодом выхода** (4.1) и **power-устройство** (1.6):
   тестовая ROM пишет «pass» или «fail» и выключает машину с кодом.
2. **Набор ISA-тестов** по образцу `riscv-tests`: по файлу на инструкцию,
   граничные значения (`DIV` на 0, `0x80000000 / -1`, сдвиги ≥ 32, знаковое
   расширение).
3. **Тесты конвейера:** цепочки зависимостей, load-use, переход сразу после
   load, `MTCR STATUS` + прерывание, fault в тени перехода (не должен
   сработать), прерывание во время `WFI`.
4. **Тесты MMU:** суперстраницы, невыровненная суперстраница, отсутствие
   `U`, `TLBI`, смена `PTBR`.
5. **Юнит-тесты `asm.py`:** кодирование каждой инструкции, диапазоны
   immediate, выражения.
6. **Эталонная модель:** простой функциональный интерпретатор (без
   конвейера) для сравнения трасс с конвейерной реализацией (lock-step
   differential testing).
7. **CI** (GitHub Actions): сборка, ассемблирование тестов и прогон
   headless.

## 7. Документация и спецификация

Спецификация и описание инструкций (`SPECIFICATION.md`, `INSTRUCTIONS.md`)
уже подробные и согласованы с кодом. Не хватает:

- ABI и соглашения о системных вызовах (см. 5);
- протокола загрузки (кто и куда грузит ОС, состояние регистров при передаче
  управления);
- описания новых устройств по мере появления;
- таблицы кодировки опкодов одним блоком (карта свободных опкодов для
  будущих расширений);
- явного правила для reserved-битов (2) и выборки из I/O (2);
- модели памяти (порядок видимости загрузок и сохранений), если появятся
  DMA, кэши или второе ядро.

## Предлагаемый порядок работ

1. **Таймер + `CYCLE`/`INSTRET` + power-устройство + headless-режим.**
   Минимальный набор, после которого можно писать тесты и планировщик.
2. **Автотесты ISA/конвейера/MMU + CI.** Закрепляют то, что уже сделано.
3. **Исправить модель исключений в supervisor (1.3) и спекулятивную
   выборку из I/O (2).**
4. **Дамп состояния, трассировка, дизассемблер, CLI.**
5. **Блочное устройство + протокол загрузки + ABI-документ.**
6. **Атомики, `MULH*`, `BREAK`, A/D-биты / ASID.**
7. **Framebuffer / текстовый видеорежим.**
8. **Линкер + формат объектников → компилятор C → libc.**
9. **Простое ядро ОС** (процессы, syscall'ы, драйвер диска, ФС) как
   итоговая проверка того, что архитектура полна.
